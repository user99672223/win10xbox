# Dispatcher and process bootstrap

`core/dispatch/` + `core/asm/` implement DECISIONS.md E1-E5: every syscall
issued by the guest (Wine's PE ntdll, later win32u) lands in one dispatcher,
and `process::Launch` boots Wine's ntdll inside the host process. Public
interface: `core/include/win10xbox/dispatch.h`.

| File | Contents |
|------|----------|
| `core/asm/syscall_entry.S` / `.asm` | entry stub (GAS for clang-mingw, MASM for MSVC; `sources.cmake` picks by `if(MSVC)`) |
| `core/dispatch/dispatcher.cpp` | table, policies, relay, statistics, generic caller, emulated handles, thread state / TEB view |
| `core/dispatch/syscall_table.gen.inc` | generated by `tools/gen_syscalls.py` from Wine's `ntsyscalls.h` |
| `core/dispatch/syscall_policy.inc` | hand-maintained policy per syscall |

| `core/dispatch/nt_process.cpp` | handle routing, memory/process/thread queries, exit, context switches |
| `core/dispatch/nt_spawn.cpp` | child processes (`NtCreateUserProcess`) and the refusals around process creation, debugging and `NtSetSystemInformation` |

## Entry contract

The loader rewrites each guest thunk (`mov r10,rcx; mov eax,id; test
[7FFE0308h],1; ...`) from byte 8 on with an absolute jump to
`dispatch::SyscallEntryAddress()`. The stub is therefore entered by `jmp`
with exactly the state the kernel would see at `syscall`:

| Register / memory | Meaning |
|---|---|
| `eax` | syscall id: the table's id for the thunk's name (Wine's numbering; native thunks are renumbered at map time, see "Dispatch by name") |
| `r10`, `rdx`, `r8`, `r9` | args 0-3 |
| `[rsp]` | return address into the guest caller (the thunk was `call`ed) |
| `[rsp+0x28+8*(i-4)]` | stack arg `i` (above the caller's 0x20 shadow space) |

The stub saves `rbx/rsi/rdi`, clears DF, keeps the stack 16-byte aligned,
copies exactly `nargs` arguments (from `win10xbox_syscall_nargs(id)`, at
most 20) into a contiguous array, builds a `dispatch::Frame`, calls
`win10xbox_dispatch(Frame*)` and `ret`s to the guest with `rax` = NTSTATUS.
Volatile registers are clobbered (the kernel clobbers `rcx`/`r11` too). The
prologue carries unwind info (`.seh_*` / `PROC FRAME`) so host exception
dispatch can walk through it.

Frame layout (`rsp` after the prologue):

```
+0x000  shadow space for our calls
+0x020  Frame { u32 id; u32 nargs; u64* args; u64 return_address; u64 guest_rsp; }
+0x040  pad
+0x050  args[20]          args[0..3] from registers, args[4..] copied from the guest stack
+0x0f0  saved rdi, rsi, rbx
+0x108  guest return address  (= Frame.guest_rsp)
+0x130  guest stack arg 4
```

## Guest view and host view of the TEB

Guest and host share one TEB per thread (E2), but Wine's `loader_init`
installs its own static-TLS array (`TEB+0x58 ThreadLocalStoragePointer`)
and FLS data (`TEB+0x17C8`) on guest threads. Host code on such a thread
(the dispatcher, the C++ runtime it uses: MSVC magic statics, CRT per-thread
data, libc++abi exception globals) needs the host's values. Each thread that
runs guest code has a `ThreadState` in a TLS slot (allocated at
`Initialize`, must be < 64 so the asm can read `TEB.TlsSlots[i]` directly);
the entry stub swaps both pointers to the host values on the way in and back
on the way out (nesting counted in `ThreadState::depth`). Host entry points
that are reached from guest code without the stub use
`dispatch::HostModeScope` (VEH handlers, scanner site handlers, the patched
Wine debug functions, the unix-call dispatcher). Calls that resume guest code
without returning (`NtContinue`, `NtContinueEx`, `NtRaiseException`,
`NtSetContextThread` on self) switch back to the guest view first.

Guest and host therefore keep separate FLS universes; `RtlFls*` is *not*
forwarded.

A guest thread starts with **no** TLS vector in the TEB (`EnterGuest` stores 0
in `ThreadLocalStoragePointer` just before calling `LdrInitializeThunk`; the
host's vector is already in `ThreadState::host_tls`). Wine's loader runs
`alloc_tls_slot` for every statically imported DLL with a TLS directory before
`alloc_thread_tls`, and it frees and replaces slot *i* of whatever vector the
TEB holds; entering with the host's vector there freed the host's own TLS
blocks (0xC0000374 on Windows as soon as a guest imported user32 -> native
advapi32 -> msvcrt). For the same reason `NtGetNextThread` enumerates guest
threads only.

### The guest-view window (no host code in here)

`LeaveToGuestView()` installs the **guest's** `ThreadLocalStoragePointer`, and
the calls it exists for (`NtContinue`, `NtContinueEx`, `NtRaiseException`,
`NtSetContextThread` on self) do not return. Between the swap and the guest
resuming, the host image has **no TLS block**, so any host code that touches
thread-local storage reads through the guest's array and faults on a near-null
address.

Under MSVC that includes code with no `thread_local` anywhere in it. A
function-local `static` emits a thread-safe-init guard that reads
`_Init_thread_epoch` at a small offset inside the host module's TLS block:

```
mov rax, [rax+rcx*8]   ; TlsArray[__tls_index]  -> NULL, no block for the host image
mov eax, [rdx+rax]     ; _Init_thread_epoch     -> reads 0x4 / 0x104
```

That is how `State& S() { static State s; ... }` in `dispatcher.cpp`, reached
through `Host()` from `Xl_NtContinue`, crashed on real Windows and on the
console while this repo's Wine job stayed green: **mingw uses `__cxa_guard`,
which touches no TLS, so the fault is unreachable under Wine.** The same
instruction bytes (`48 8b 04 c8` / `8b 04 02`) appeared in both reports.

The rule is therefore that the window contains no host code at all:

- Everything a transfer needs is resolved **before** the swap.
  `CallInGuestView(Host().NtX, ...)` makes the compiler guarantee that, because
  arguments — the function pointer included — are evaluated before the call. Use
  it instead of writing the swap out by hand.
- Only these may run inside it, and they must stay free of TLS, lazy
  initialisation and logging: `CurrentThreadState`, `SwapIn`/`SwapOut`,
  `LeaveToGuestView`, `ReenterHostView`, `GuestViewActive`, `core/asm`. That is
  why `CurrentThreadState` only bumps a counter on a bad slot and leaves the
  reporting to `win10xbox_dispatch`.
- `dispatcher.cpp`'s process state is a `constinit` object at **namespace
  scope**, not a function-local `static`: no guard, no TLS, and the compiler
  rejects any future member that would need dynamic initialisation. Do not turn
  it back into a function-local static.

**Detection, which is the part Wine can do.** `LeaveToGuestView` sets
`kThreadGuestView` in `ThreadState::flags`; `GuestViewActive()` reports the
window as open while that flag is set *and* `ThreadState::depth` is 0 — depth is
what distinguishes "the guest is running" from "we are back in host code",
because the asm entry stub and `HostModeScope` both raise it, and the
non-returning calls mean the flag alone would never be cleared. The singleton
accessors in `core/dispatch` call `NoteHostStateUnderGuestView()`, and
`trace::Log` consults a probe the dispatcher registers so a stray `TRACE` in the
window is dropped and counted rather than faulting on its own mutex. Neither can
log from inside the window, so both only count; `win10xbox_dispatch` reports
them once from the host view, naming the culprit.

`integration.guest_view_clean` asserts zero violations on a normal guest run and
**fails under Wine if the `LeaveToGuestView()`-then-`Host()` ordering comes
back**, which is the only defence linux-cross can offer against this class.
`integration.guest_view_violation_detected` drives
`WIN10XBOX_TEST_GUEST_VIEW_VIOLATION=1` to prove the detector still works.

`/Zc:threadSafeInit-` would also remove the guard, and is **not** used: it drops
thread-safe initialisation for every function-local static in `core/`, and
several of them (`Threads()`, `Objects()`, `ExportCache()`, the `trace`
singletons) are first touched from guest threads created at arbitrary times, so
their initialisation is not provably ordered before concurrency.

### User-mode callbacks in native GUI mode

With `gui = native` (docs/GUI.md "Route B: native win32k") win32u syscalls go to the host's real win32k,
which calls back into user mode: the kernel enters the **host** ntdll's `KiUserCallbackDispatcher` on the
thread that made the syscall, below that syscall's frame on the same stack, and it calls
`PEB.KernelCallbackTable[i](args, len)`. The callback normally ends in `NtCallbackReturn`, which makes the
kernel discard the callback's stack and complete the *original* syscall. `core/dispatch/win32k_native.cpp`
puts 512 trampolines in the PEB once the guest's user32 has installed its table (checked before every win32u
pass-through); trampoline `i` routes by thread: a thread without a guest `ThreadState` (host-uwp's CoreWindow,
a composer thread) gets the host's user32 `host_table[i]` exactly as before; a guest thread gets
`CallInGuestView(guest_table[i], args, len)`.

The sequence on a guest thread, with `ThreadState::depth` (asm = `core/asm/syscall_entry.{S,asm}`):

| step | where | depth | TEB TLS/FLS |
|---|---|---|---|
| guest calls `NtUserX` | guest | 0 | guest |
| asm entry: `++depth` (0->1), `SwapIn` | asm | 1 | host |
| `win10xbox_dispatch` -> host win32u thunk -> `syscall` | host | 1 | host |
| kernel callback -> `KiUserCallbackDispatcher` -> trampoline `i` | host | 1 | host |
| `CallInGuestView`: `LeaveToGuestView()` saves `d = 1`, `depth = 0`, `SwapOut` | window | 0 | guest |
| guest user32 `__fnXXX` -> window procedure (nested syscalls repeat this table one level down) | guest | 0 | guest |
| guest calls `NtCallbackReturn` (Wine ntdll thunk) -> asm entry: `++depth` (0->1), `SwapIn` | asm | 1 | host |
| dispatcher: PassThrough to the host's `NtCallbackReturn`; the kernel unwinds to the original syscall | host | 1 | host |
| the host win32u thunk returns into `win10xbox_dispatch`, which returns to the asm | host | 1 | host |
| asm exit: `--depth` (1->0), `SwapOut` | guest | 0 | guest |

**Invariant: at every kernel transition the depth counter and the installed TLS view agree with the frame the
kernel resumes.** `NtCallbackReturn` enters through the asm stub, which raises depth to exactly the value the
interrupted syscall's frame had when it entered the kernel (1 for a direct guest syscall, n+1 when the syscall
was made at depth n), and installs the host view, which is what that frame had too. So when the kernel
abandons the callback stack (the trampoline, `CallInGuestView` with its saved `d`, the stub frame of
`NtCallbackReturn`) nothing that was abandoned still has to be undone: `ReenterHostView(d)` is skipped, but the
asm entry of `NtCallbackReturn` already did its work, and `guest_tls`/`guest_fls` in the `ThreadState` hold the
same thread's guest pointers. The `kThreadGuestView` flag stays set, as after `NtContinue`; `GuestViewActive()`
also requires `depth == 0`, so it reports correctly. A callback that **returns** to the trampoline instead
takes the ordinary way: `ReenterHostView(d)` restores depth and the host view, the trampoline returns the
status to `KiUserCallbackDispatcher`, and the host ntdll makes the `NtCallbackReturn` itself. Nothing between
the swap and the guest call is host code (`CallInGuestView` resolves the target first), and the per-callback
trace line is written before it, from the host view. Rules this relies on: nothing may hold a lock or own a
resource across a win32u pass-through (the kernel may unwind through the trampoline frames, never through
`win10xbox_dispatch`'s), and `NtCallbackReturn` stays PassThrough in native mode (Emulate in emulated mode,
where core/user runs the callback itself).

### The TLS slot we hold

`ThreadLocalStoragePointer` and `FlsData` are *pointers*, so swapping them gives
guest and host an array each and an index collision between the two allocators
is harmless. `TEB.TlsSlots` (TEB+0x1480) is different in kind: it is an **inline
64-entry array inside the TEB**, not reachable through a swappable pointer, so it
cannot be given per-view copies. Our `ThreadState` pointer lives in it, which
makes it the one per-thread surface the guest's `TlsAlloc` and we share. Three
things keep that safe:

1. **The two allocators coordinate through the PEB.** `PEB.TlsBitmap` (0x78)
   points at an `RTL_BITMAP` whose *bit storage* is `PEB.TlsBitmapBits` (0x80),
   inside the PEB itself — both for Microsoft's ntdll and for Wine's, which
   re-points `PEB.TlsBitmap` at its own `RTL_BITMAP` but passes
   `peb->TlsBitmapBits` as the buffer (`wine-src/dlls/ntdll/loader.c:4450`).
   `RtlInitializeBitMap` only stores `Buffer`/`SizeOfBitMap`, it does **not**
   clear the bits (`rtlbitmap.c:73`), so a bit our host `TlsAlloc` set before the
   take-over is still set afterwards and the guest's allocator skips it.
   `ReserveGuestTlsSlot` verifies exactly that once the guest has installed its
   bitmap, sets the bit if it was clear, and says which it found — the "already
   in use" trace line is the evidence that the two really do share the storage on
   that host.
2. **We never hold an index Wine claims by fiat.** `loader_init` does not
   *allocate* indices 0 and `NTDLL_TLS_ERRNO` (16), it asserts them with
   `RtlSetBits` after the fact (`loader.c:4454`), and `_errno()` then hands out
   `&TEB.TlsSlots[16]` as the storage for an `int`
   (`wine-src/dlls/ntdll/thread.c:445`). A bitmap cannot protect us there, so
   `Initialize` takes indices until it gets one at or above 19
   (`WOW64_TLS_MAX_NUMBER`), keeps the highest usable one and frees the rest. The
   index it settled on is always traced on the `dispatch` channel. The WoW64
   block only matters when `TEB.WowTebOffset != 0`, which never happens for our
   x64-only guests, but preferring an index above it is free.
   `PEB.TlsExpansionBitmap` needs no such care: expansion indices address
   `TEB.TlsExpansionSlots`, a separately allocated array, never `TEB.TlsSlots`
   (`wine-src/dlls/kernelbase/thread.c:788`), and our index must be < 64 anyway.
3. **The slot is stored tagged, and validated before it is dereferenced.** What
   goes into the slot is `pointer | ((0x8000 | bits 16..30 of pointer) << 48)`,
   using the always-zero top 16 bits of an x64 user address. An errno-style
   collision is a **4-byte** write into an 8-byte slot, so it leaves a non-NULL
   value with the low dword gone — which the old bare `test rbx,rbx` passed
   straight through, after which `SwapIn` read `host_tls`/`host_fls` out of a
   wild pointer and installed them in the TEB. Comparing the tag against the
   pointer's own bits catches that arithmetically, with no memory access, so
   nothing bogus is ever dereferenced. Both asm twins do it identically and
   count failures in `win10xbox_thread_slot_clobbered`; `win10xbox_dispatch`
   reports the first one and puts our pointer back. `CurrentThreadState()`
   additionally checks `ThreadState::magic`, which rejects a stale pointer to an
   already-detached state.

Test hooks (both no-ops unless the variable is set, and both read before the PEB
take-over, since the guest's environment block replaces the host's):
`WIN10XBOX_TEST_TLS_INDEX=<n>` asks for a specific index (`!<n>` forces one past
the guard) and `WIN10XBOX_TEST_TLS_CLOBBER=1` performs the 4-byte store at guest
entry. They exist because none of this is reachable by accident under Wine: there
the host ntdll *is* Wine's, so index 16 was reserved before our `TlsAlloc` ran.
`integration.guest_tls_slot_intact`, `guest_tls_slot_clobber` and
`guest_tls_reserved_index` use them to gate all three properties above on the
linux-cross job.

## Policies

`syscall_policy.inc`, one line per syscall, read by the dispatcher and by the
table generator:

```
POLICY(NtAllocateVirtualMemory, PassThrough, "")
POLICY(NtCreateFile, Translate, "VFS path rewrite")
POLICY(NtOpenKey, Emulate, "registry")
```

Anything not listed is `Todo`. At `Initialize` every entry gets `host_fn`
(GetProcAddress on the host's own ntdll, never the guest's) and `impl` (from
the implementation lists in `nt_*.cpp` / `subsystems.cpp`).

| Policy | Execution |
|---|---|
| `PassThrough` | `host_fn(args...)` via `CallWithArgs` (always passes 20 args; callees ignore extras) |
| `Translate` | `impl(args...)`: rewrites inputs, calls the host, fixes outputs |
| `Emulate` | `impl(args...)`: never touches the host resource |
| `Todo` | `fixme:dispatch:... unimplemented syscall NtFoo`, returns `STATUS_NOT_IMPLEMENTED` |

A `Translate`/`Emulate` entry whose implementation is not built (subsystem
module switched off with `-DWIN10XBOX_HAVE_<SUB>=OFF`) falls back to
pass-through with a WARN, except names in `NeverPassThrough()` (currently
`NtSetSystemTime`), which become `Todo`. `SetPolicy()` changes an entry at
run time; `process::Launch` applies machine.json `"syscall_overrides"`
(`passthrough|translate|emulate|todo`) through it.

### Tracing

Channels (`WIN10XBOX_DEBUG`, WINEDEBUG syntax): `relay` logs every syscall
after it returns,

```
0024:trace:relay: NtCreateFile(00007ffffee1f450,00100080,...) ret=00000000
```

(args in hex, 8 digits when they fit in 32 bits, else 16; `nargs` from the
table; the upper half of 32-bit arguments is whatever the caller left there).
`+timing` appends ` (12.3us)`. Calls that may not return (`NtContinue`,
`NtTerminate*`, `NtRaiseException`) are logged before the call as well.
`dispatch::Shutdown()` dumps per-syscall call counts on `relay`. Other
channels: `dispatch` (table, mappings, forwarding), `process` (bootstrap,
exit), `wine` (output of Wine's own debug channels, see below), `user`
(core/user: windows, classes, messages, painting) and `gdi` (core/user: GDI
objects, DCs, drawing).

## Object manager namespace (`nt_object.cpp`, `ob_namespace.cpp`)

What a Windows program sees of the object manager, kept in the layer so that it does not depend on what the host's own
namespace allows (Wine's server has no `\Sessions`, the console's AppContainer may not open `\BaseNamedObjects`).

**The tree.** `ob::Tree` (ob_namespace.cpp, pure, unit-tested) holds directory objects, symbolic links and kernel-provided
leaves. Lookup follows `ObpLookupObjectName`: `STATUS_OBJECT_PATH_SYNTAX_BAD` (no leading `\` and no root, or a rooted name
under a root handle), `STATUS_OBJECT_NAME_INVALID` (empty component, trailing `\` after an existing directory),
`STATUS_OBJECT_PATH_NOT_FOUND` (a missing component with more path after it), `STATUS_OBJECT_NAME_NOT_FOUND` (missing leaf),
`STATUS_OBJECT_TYPE_MISMATCH` (a link or a leaf used as a directory, a directory opened as another type), case sensitivity
only with `OBJ_CASE_INSENSITIVE`, symbolic links followed in the middle of a name and at the end unless the caller asks
for the link (`NtOpenSymbolicLinkObject`, `NtCreateSymbolicLinkObject`). A miss directly in the root `\` is not ours:
the name goes to the host or the VFS as before (`\Device`, `\Registry`, `\KnownDlls`...), a link that leads there hands
back the name to continue with.

Layout, built at `Initialize` for the session in `PEB.SessionId` (host value; `<n>` below):

```
\                                  (listing = the tree + the host's own top-level directories)
\BaseNamedObjects                  Global, Local (-> \BaseNamedObjects), Session (-> \Sessions\BNOLINKS)
\Sessions\BNOLINKS\<n>             -> \Sessions\<n>\BaseNamedObjects
\Sessions\<n>\BaseNamedObjects     Global (-> \BaseNamedObjects), Local (-> itself), Session
\Sessions\<n>\AppContainerNamedObjects[\<sid>]    <sid> only when the host process is an AppContainer (the console)
\KernelObjects  \ObjectTypes
\??  (misses continue in \GLOBAL??)   \DosDevices -> \??
\GLOBAL??                          drive letters from core/vfs (C: -> \Device\HarddiskVolume1...), PIPE, MAILSLOT, UNC, NUL,
                                   GLOBALROOT (-> ""), Global
```

Directories and links created by a guest are nodes with a pin per handle: a temporary one disappears with its last handle
(and a directory with its last child), `OBJ_PERMANENT` keeps it, `NtMakeTemporaryObject` ends that. Their handles are
emulated (`ObjectKind::Directory` / `SymbolicLink`), so `NtClose`, `NtDuplicateObject` and `NtQueryObject` (basic, name,
type with the host's real mappings and masks) are answered here. `NtQueryDirectoryObject` fills the real
`OBJECT_DIRECTORY_INFORMATION` array (rows, an all-zero row, then the NUL-terminated strings) with Windows' `context`,
`STATUS_MORE_ENTRIES`, `STATUS_NO_MORE_ENTRIES` and `STATUS_BUFFER_TOO_SMALL` rules (`ob::PackDirectoryEntries`).

**Named kernel objects.** Events, mutexes, semaphores, timers, sections, keyed events, I/O completions, jobs and reserve
objects are created by the host. A name that resolves to a free leaf in one of our directories becomes
`<host named-object directory>\W10X<layer>!<escaped guest path>` (`ob::MangleName`: `\` -> `|`, `|` and `%` percent
escaped; a path whose escaped form exceeds 200 characters is named `W10X<layer>#<hash>` and remembered by the process that
used it). The host directory is the one the host itself uses for a `Local\` object, found at start-up with a probe event
(`\Sessions\1\BaseNamedObjects` on a desktop, `\Sessions\<n>\AppContainerNamedObjects\<sid>` in the console's
AppContainer, whatever Wine's server uses under Wine). The layer prefix is 16 hex digits: the first process of a
program tree draws it and puts it in its host environment as `WIN10XBOX_OBJNS`, children get it with the other host-owned
variables (`NtCreateUserProcess`), so a guest and the children it starts share one set of names and nothing else does.
Waits, access checks, security and `OBJ_OPENIF` / `STATUS_OBJECT_NAME_EXISTS` / collision answers are the host's;
arguments are checked before the name (an invalid event type is `STATUS_INVALID_PARAMETER` whatever the name), by asking
the host about an unnamed object of the same kind. `NtQueryObject(ObjectNameInformation)` of such a handle decodes the host
name back to the guest path, so a child sees the right name on an inherited handle too. A directory listing is the
tree's children plus the host directory's objects that carry this layer's prefix (when the host lets the process list it)
plus what this process holds open (when it does not).

Limits. Directories and links a guest creates exist in that process only: a child sees the layout above and the named
objects by their full guest path, but not a directory its parent made (the object under it is found only when the
directory also exists in the child). `NtCreateDebugObject` stays `STATUS_NOT_SUPPORTED` (E6) and window stations are
not objects (core/user), so the `om` unit stops there (docs/slices/om.md). `OBJ_PERMANENT` on a directory or link is
honoured without the `SeCreatePermanentPrivilege` check. File names that go through the tree (`\BaseNamedObjects\x`, a
name relative to one of our directory handles, a link the guest made in `\??`) are resolved here first
(`ResolveFileNameThroughNamespace`, called from `TranslateOA`): a directory is `STATUS_OBJECT_TYPE_MISMATCH`, a name the
tree does not know `STATUS_OBJECT_NAME_NOT_FOUND`, and a link that leads out (`\Device\Null`) continues with that name.

## Child processes (`NtCreateUserProcess`, D1/E7)

Wine's kernelbase `CreateProcessInternalW` builds an `RTL_USER_PROCESS_PARAMETERS`, calls `NtCreateUserProcess` with the
thread suspended (`THREAD_CREATE_FLAGS_CREATE_SUSPENDED`, always) and `NtResumeThread`s it itself unless the caller said
`CREATE_SUSPENDED`. Wine's own unix side asks wineserver to build the process; there is no wineserver here, so
`nt_spawn.cpp` builds the child out of **a new host process running the host executable again**:

```
"<win10xbox.exe>" --machine <machine root> [--cwd <guest dir>] [--guest-env] [--cmdline <raw guest command line>] <guest image>
```

`<win10xbox.exe>` is `GetModuleFileNameW(NULL)`, read in `dispatch::Initialize` (afterwards the PEB's loader list is the
guest's and the call would name the guest EXE); the kernel32 process-creation entry points are resolved there too, for
the same reason and because the UWP host's import library does not carry them. host-win32's `main` turns the command line
back into `process::LaunchOptions` (`--cmdline`, `--guest-env`; the rest is its ordinary command line), boots a second,
independent layer in the child and returns the guest's exit code as the host process's, which `NtWaitForSingleObject` /
`NtQueryInformationProcess(ProcessBasicInformation)` on the handle then report (host handles pass through).

What the caller's arguments become:

| Guest argument | Host child |
|---|---|
| `PS_ATTRIBUTE_IMAGE_NAME` (`\??\C:\x.exe`) | the guest Win32 path after `--machine`; read through the VFS first: missing file `STATUS_OBJECT_NAME_NOT_FOUND`, no `MZ` `STATUS_INVALID_IMAGE_NOT_MZ` (so kernelbase falls back to `cmd.exe /c` for `.bat`), a DLL or a non-x64 machine `STATUS_INVALID_IMAGE_FORMAT` (D6), and `PS_CREATE_INFO.State` says which stage failed |
| `params->CommandLine` | `--cmdline`, quoted so the host's argv parse returns it unchanged; the child sees the bytes the parent wrote, not a rebuilt argv |
| `params->CurrentDirectory` | `--cwd` (guest path) and, through the VFS, the host child's own working directory |
| `params->Environment` | the child's host **environment block**: the guest's entries, then the host-owned variables (`WIN10XBOX_*`, `WINE*`, copied from the parent host's original block) so the host process itself stays configured (`WIN10XBOX_DEBUG`, `WINEDEBUG`); `--guest-env` tells the child to take everything else as its guest environment (`process::InheritedGuestEnvironment`). A guest variable with a host-owned name is dropped |
| `params->hStdInput/Output/Error` | the host child's `STARTUPINFO` standard handles. A handle that is not inheritable is duplicated as one for the duration of the call (Windows would hand the child a dead value); an invalid one is dropped with a warning |
| `PROCESS_CREATE_FLAGS_INHERIT_HANDLES`, `PS_ATTRIBUTE_HANDLE_LIST` | `bInheritHandles` and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` (the standard handles are always added to a list); without INHERIT_HANDLES only the standard handles are inherited |
| `PS_ATTRIBUTE_PARENT_PROCESS`, `PS_ATTRIBUTE_JOB_LIST` | the same host attributes; a parent that is this process is ignored |
| `THREAD_CREATE_FLAGS_CREATE_SUSPENDED`, `PROCESS_CREATE_FLAGS_SUSPENDED` | `CREATE_SUSPENDED`; `NtResumeThread` is a pass-through on the host thread |
| `PROCESS_CREATE_FLAGS_BREAKAWAY`, `ConsoleFlags & 1` (new process group), `CONSOLE_HANDLE_ALLOC_NO_WINDOW`, no console (`DETACHED_PROCESS`) | `CREATE_BREAKAWAY_FROM_JOB`, `CREATE_NEW_PROCESS_GROUP`, `CREATE_NO_WINDOW`, `DETACHED_PROCESS`. `CONSOLE_HANDLE_ALLOC` (new console, or none in the parent) leaves the host's console alone: the layer has no consoles of its own and a console window opened for it would be wrong |
| `dwX..dwFillAttribute`, `dwFlags & 0xFF`, `wShowWindow` | `STARTUPINFO` window placement and feedback bits |
| outputs | process and thread handles (the host child's, full access; `OBJ_INHERIT` honoured), `PS_ATTRIBUTE_CLIENT_ID` (host pid/tid), `PS_ATTRIBUTE_IMAGE_INFO` (`SECTION_IMAGE_INFORMATION` read from the file: entry point, stack sizes, subsystem, machine, `ImageFileSize`), `PS_CREATE_INFO` (`Size`, `State = PsCreateSuccess`). `PS_ATTRIBUTE_TEB_ADDRESS` is left alone |

Refused, with a warning that names the reason: `PS_ATTRIBUTE_TOKEN` (the guest's tokens are emulated; a host child cannot
run under one) and a non-null `PS_ATTRIBUTE_DEBUG_PORT` (`STATUS_NOT_SUPPORTED`), a machine type other than x64, an image
path that is not a drive-letter path (`STATUS_OBJECT_PATH_NOT_FOUND`), `THREAD_CREATE_FLAGS_HIDE_FROM_DEBUGGER`
(`STATUS_INVALID_PARAMETER`, as in Windows and Wine). Other process/thread flags and unknown input attributes are logged
as FIXMEs and ignored, as Wine does.

`config::Config::child_processes` selects it. host-win32 turns it on; the UWP host cannot create processes and leaves it
off, where `NtCreateUserProcess` traces a warning and returns `STATUS_NOT_SUPPORTED`. Limits worth knowing: the child
knows the machine folder and `machine.json` but not drives mapped at run time by `process::MapHostDirectory` (a host path
outside the machine folder given to the first `win10xbox.exe`); every child boots its own Wine ntdll, so a child costs a
full start (a second or so under Wine); there is no process tree or session sharing, so Wine-only mechanisms that need
wineserver (`CreateProcess` of a Unix binary, `winevdm`) do not apply; the machine folder must provide the program: the
builtin set built by `wine-pe` does not contain `cmd.exe`, so `CreateProcess("cmd.exe ...")` and `system()` find
nothing until a `cmd.exe` is staged. `NtCreateProcessEx` (an empty process to be filled in with `NtWriteVirtualMemory` and
a later thread) and the legacy `NtCreateThread` (caller-allocated stack and arbitrary `CONTEXT`; guest threads enter
Wine's per-thread loader init, E4) answer `STATUS_NOT_SUPPORTED` with a FIXME; nothing in Windows 10 user mode calls them.

`NtSetSystemInformation` (E8): the classes in `kPrivilegedClasses` (`nt_spawn.cpp`: 44 of them, each with the privilege
Windows asks for) answer `STATUS_PRIVILEGE_NOT_HELD` and so does every class not listed as safe; `SystemComPlusPackage`
(59, settable without a privilege, changes a counter) reaches the host. `kernelbase!SetSystemTimeAdjustment` and the time
zone setters therefore fail with `ERROR_PRIVILEGE_NOT_HELD`, as they do for an unprivileged Windows user, and the virtual
clock and the machine identity stay the layer's.

## Wine "unix side"

`__wine_unix_call_dispatcher` (a data export of Wine's ntdll) is set to
`dispatch::UnixCallDispatcher`; `__wine_unixlib_handle` to ntdll's handle.
Handles are `index+1` into `RegisterUnixLib` registrations, looked up by
module base name (`ntdll.dll` / `ntdll.so` -> `ntdll`). ntdll's table
(`dlls/ntdll/unixlib.h` order):

| Call | Result |
|---|---|
| `load_so_dll` | `STATUS_DLL_NOT_FOUND` |
| `unwind_builtin_dll` | `STATUS_UNSUCCESSFUL` |
| `wine_dbg_write` | raw text to channel `wine` |
| `wine_server_call` | `fixme:wine:` once per request id, `STATUS_NOT_IMPLEMENTED` |
| `wine_server_fd_to_handle`, `wine_server_handle_to_fd`, `wine_spawnvp` | `STATUS_NOT_SUPPORTED` |
| `system_time_precise` | `clock::SystemTime100ns()` (host precise time without the clock module) |

Wine's PE ntdll keeps its debug-channel table at `PEB+0x2000` and per-thread
debug buffers at `TEB+0x3000` (its unix side allocates PEB/TEB with that
room). A host PEB/TEB has neither, so `__wine_dbg_get_channel_flags`,
`__wine_dbg_header`, `__wine_dbg_output` and `__wine_dbg_strdup` are
redirected to `core/dispatch` (`WINE_OVERRIDE` in `rtl_forward.inc`). Output:
`0024:fixme:wine:ntdll:LdrFoo text`. fixme/err follow the `wine` channel;
per-Wine-channel classes come from `WIN10XBOX_WINEDEBUG` (WINEDEBUG syntax,
e.g. `+loaddll,warn+module`; a separate variable so a Wine host is not
affected).

## Function-level forwarding (E2)

`rtl_forward.inc` lists guest ntdll exports replaced by a 5-byte `jmp` (via a
near trampoline when out of rel32 range) to the same-named host export, while
the image is still writable: heap, critical sections, SRW/condition
variables/run-once, exception dispatch/unwind/function tables/VEH. Each
group's reason is in the file. Not forwarded on purpose:
`KiUserExceptionDispatcher` (the kernel only calls the host's),
`RtlQueryPerformanceCounter/Frequency` (clock), `RtlFls*` (separate FLS, see
above). A missing host export is a WARN and Wine's copy stays. `.pdata` is
checked so a jump never overwrites the next function.

## Bootstrap sequence (`process::Launch`)

1. `dispatch::Initialize()`; `vfs::Initialize(machine_root)` (machine.json:
   version, identity, clock, cpu, syscall_overrides), then registry, clock,
   token with those settings; CPU policy; ntdll unix lib registration.
2. Map `<machine>\Windows\builtin\ntdll.dll` through the same image-section
   path (ReserveOnly, at its preferred base when free): stubs rewritten,
   cpuid/rdtsc scanned, Rtl forwarding + Wine debug overrides applied,
   `__wine_unix_call_dispatcher` / `__wine_unixlib_handle` written, then
   final protections.
3. Open the guest EXE through `Xl_NtOpenFile` (VFS), `Xl_NtCreateSection
   (SEC_IMAGE)`, `Xl_NtMapViewOfSection`: the EXE is scanned like every other
   image. x64 EXEs only (D6).
4. Create the guest main thread (stack reserve = EXE `SizeOfStackReserve`, at
   least 1 MiB). It runs the host's per-thread init, attaches its
   `ThreadState`, then waits: the host's thread init must still see the host
   PEB (a Wine host looks up `Peb->ImageBaseAddress` in its module list).
5. PEB take-over (below), then release the thread. It probes 80 KiB of stack
   (Wine's `signal_start_thread` clears 60 KiB below the CONTEXT), builds a
   CONTEXT (`RtlCaptureContext`; `Rip` = guest `RtlUserThreadStart`, `Rcx` =
   EXE entry, `Rdx` = PEB, `Rsp` = stack top - 0x100, 16-byte aligned - 8) and
   calls the guest `LdrInitializeThunk(&ctx, 0, 0, 0)`.
6. Wine's `loader_init` installs its loader lists, TLS bitmaps (over the
   PEB's own bits), copies the process parameters, reads the version and
   locale, loads kernel32/kernelbase (and the CRT) from the machine folder,
   runs DllMains; `signal_start_thread` then `NtContinue`s into
   `RtlUserThreadStart` -> `BaseThreadInitThunk` -> EXE entry.
7. `ExitProcess` -> `RtlExitUserProcess` -> `NtTerminateProcess(NULL)`
   (other guest threads killed) -> `LdrShutdownProcess` ->
   `NtTerminateProcess(-1)` -> `GuestExit`: record the code, restore the PEB,
   signal, terminate the guest thread. `Launch(wait=true)` returns the code;
   host-win32 returns it from `wmain`.

With `run_on_new_thread = false` the calling thread becomes the guest main
thread and never returns: `GuestExit` ends the host process with the
guest's code.

### PEB fields we take over (restored at guest exit)

| Field | Guest value |
|---|---|
| `ImageBaseAddress` (0x10) | guest EXE base |
| `ProcessParameters` (0x20) | new block from host `RtlCreateProcessParametersEx` (normalized; every string with `MaximumLength = Length + 2` and NUL-terminated, since the block packs its strings back to back and `GetCommandLineW` returns the pointer as is), moved into its own `VirtualAlloc` region because Wine releases the old block with `NtFreeVirtualMemory`; guest image path, command line, current directory (default `C:\Users\User\`), `DllPath` NULL (Wine computes it), guest environment; console handle and std handles copied from the host block |
| `OSMajorVersion`/`OSMinorVersion`/`OSBuildNumber`/`OSCSDVersion`/`OSPlatformId` | from machine.json (10.0.19045, 0, 2); Wine's `version_init` then sets its own (registry or its WIN10 default 10.0.19045) |
| `Ldr`, `FastPebLock`, `TlsBitmap`, `TlsExpansionBitmap`, `LoaderLock`, `Ansi/OemCodePageData`, `UnicodeCaseTableData` | installed by Wine's `loader_init`/`locale_init`. The `TlsBitmap` *pointer* is saved and restored; its *bits* are `PEB.TlsBitmapBits` (0x80), which both allocators share on purpose — see "The TLS slot we hold" |
| `ActivationContextData` (0x2F8) | Wine's `actctx_init` stores its own `process_actctx` (the static `system_actctx` in the guest ntdll when the EXE has no manifest) — a Wine `ACTIVATION_CONTEXT`, not Microsoft's `ACTIVATION_CONTEXT_DATA` blob. Saved and restored; left alone, the resumed host's ntdll would read a structure of the wrong format from the guest's image on every SxS lookup (`WIN10XBOX_TEST_LEAK_GUEST_ACTCTX=1` reinstates that, for tests) |
| `ProcessHeap` | kept: the host's (wine-pe patch 0001) |

## Guest threads (E4)

`NtCreateThreadEx` on the current process creates a host thread whose start
routine is `GuestThreadProc`: the host's per-thread init runs first, then the
thread attaches a `ThreadState` and enters Wine's `LdrInitializeThunk` like
the main thread (`RtlUserThreadStart(start, arg)`). On a Wine host the
host's thread attach is skipped (`THREAD_CREATE_FLAGS_SKIP_THREAD_ATTACH`,
cleared again in the TEB before entering the guest) because Wine's host loader
looks up `Peb->ImageBaseAddress`.

## Machine folder layout

```
<machine>\machine.json                    machine/machine.default.json if missing
<machine>\Windows\builtin\*.dll           Wine PE builtins (wine-pe/out/builtin), ntdll.dll required
<machine>\Windows\System32\*.dll          native DLLs (machine/import_windows_dlls.ps1)
<machine>\Windows\System32\config\        registry hives (optional)
<machine>\Windows\Temp\
<machine>\Users\User\AppData\Local\Temp\  <machine>\Users\User\AppData\Roaming\
<machine>\ProgramData\  <machine>\Program Files\  <machine>\Program Files (x86)\
```

The integration tests use `<build>\bin\machine` (CMake cache
`WIN10XBOX_MACHINE_DIR`), prepared by `tests/integration/prepare_machine.cmake`
(test `integration.prepare_machine`, target `prepare_machine`): builtins from
`WIN10XBOX_BUILTIN_DIR` (default `wine-pe/out/builtin`) and the test programs
from `<build>\bin\guest\` into `<machine>\guest\`. Without
`Windows\builtin\ntdll.dll` the guest tests print `SKIP:` and are reported as
skipped.

## host-win32

```
win10xbox [--machine <dir>] [--debug <spec>] [--cwd <guestdir>] <program> [args...]
```

(`--cmdline <raw>` and `--guest-env` are added by the layer itself when a guest starts a child, see "Child processes".)

`--machine` defaults to `<dir of win10xbox.exe>\machine`. `<program>` may be a
guest path (`C:\guest\app.exe`, existing under the machine folder), a host
path inside the machine folder (untranslated to `C:\...`), or another host
file: its directory becomes drive `Z:` for the run when the build has no VFS
module; with the VFS such files must be listed in machine.json `"drives"`
(clear error otherwise). The exit code is the guest's.

The host ends the process with `TerminateProcess(GetCurrentProcess(), exit code)` once the layer is shut down, not by
returning from `wmain`. The normal way out (CRT `exit()` -> `ExitProcess` -> `DllMain(DLL_PROCESS_DETACH)` of every DLL)
terminates every other thread first and then runs code in DLLs the host does not own — on the first real-Windows run that
got that far, combase.dll (pulled in by dbghelp.dll, which the crash capture loads) raised an unhandled
`STATUS_INVALID_PARAMETER` there and the guest's exit code was lost. `WIN10XBOX_NORMAL_EXIT=1` takes the normal way out
for diagnosis; `tests/host_exit` gates that nothing a DLL does at detach can change the exit code.

## How to add a syscall implementation

1. Pick the policy in `core/dispatch/syscall_policy.inc` (`Translate` when
   the host still does the work, `Emulate` when it must not see it) with a
   short note.
2. Write `static NTSTATUS NTAPI Xl_NtFoo(...)` with the exact NT signature in
   the matching `nt_*.cpp` (or a `Reg_/Tok_/Clk_` function in a subsystem,
   wired in `subsystems.cpp`) and add `{"NtFoo", &Xl_NtFoo}` to that file's
   `*Impls()` list. Call the host through `Host().NtFoo` (add the pointer to
   `HostNt` in `internal.h` and `ResolveHost` in `dispatcher.cpp`) or
   `CallWithArgs(HostExport("NtFoo"), ...)`.
3. Guest pointers may be bad: validate before dereferencing (the host
   syscalls themselves return `STATUS_ACCESS_VIOLATION`).
4. Code that resumes guest code without returning must call
   `LeaveToGuestView()` first.
5. Add a test in `tests/unit/test_dispatch.cpp` (`MakeThunk(id)` calls
   through the real asm entry).

win32u (`WIN32U_SYSCALL` lines in the generated table, ids 0x1000+) goes
through the same entry; the table already reserves ids up to 0x1FFF.

## Dispatch by name

The id a thunk loads is that DLL build's numbering: Wine's for the builtins (which is what the table is keyed
by), a Windows build's for a native `win32u.dll` (build 26100: `NtUserCreateWindowEx` = 0x106F, which in
Wine's numbering is another function). `MapImageView` therefore calls `RenumberSyscallThunks` right after
`loader::RewriteSyscallStubs`: every rewritten thunk's `mov eax, imm32` (thunk+4) is set to the table id for
the thunk's **name** (VirtualProtect around the four bytes; the loader's protected-range bookkeeping is
unchanged). For Wine's DLLs this changes nothing. A name with no entry gets id 0x1FFF, which no entry has, so it
dispatches as "unknown syscall" with a FIXME at map time naming it, and never as whatever entry its foreign id
collides with. In native GUI mode a `NtUser*`/`NtGdi*` name the host's `win32u.dll` exports gets an entry of its
own instead (ids 0x1800.., PassThrough, 20 arguments copied), because route B forwards the whole win32u surface.
