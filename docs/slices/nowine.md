# Slice: no trace of Wine in the builtins

Goal: nothing a guest program can observe in the PE builtins we ship says "Wine". `fastfetch` printed
`Kernel: Wine_11.9 10.0.19045.3803` because ntdll exported `wine_get_version`; the gate in ci.yml now wants
`^Kernel: 10\.0\.19045`. Everything is done in the wine-pe build (patches and compiler flags); the behaviour of the
builtins is unchanged.

CI runs (head, wine-pe.yml, ci.yml): see the end of this file.

## What was done

* **(a) Exports by ordinal.** `patches/0006` (generated by `wine-pe/gen-nowine.py`): every `wine_*` / `__wine_*` export of
  the modules in `dlls.txt` is `-noname`: 16 in ntdll, 2 in kernel32 (`wine_get_unix_file_name`, `wine_get_dos_file_name`),
  1 in imm32 (`__wine_ime_wnd_proc`), 19 in all (win32u's `Wow64Transition` is i386 only). winebuild only accepts `-noname`
  together with an explicit ordinal, so the numbers they had are written into the spec (ntdll 1449-1464, kernel32
  1357-1358, imm32 136) and the entry that has ordinal 1 gets it written out too (winebuild takes the lowest explicit
  ordinal as the table base). Import libraries are generated from the same spec, so every module that imports one of
  them binds by ordinal. The export tables of the other modules are unchanged. **Exports kept named: none.**
  Four places looked such an export up by name and would have broken; they look it up by ordinal now (same patch):
  `libs/winecrt0/unix_lib.c` (`__wine_unix_call_dispatcher`, used by every module with a unix library: bcrypt, ws2_32,
  netapi32, secur32, dnsapi, win32u), `win32u` `DllMain` (`__wine_syscall_dispatcher`), `user32` (`__wine_ime_wnd_proc` in
  imm32) and the conformance framework's Wine detection in `include/wine/test.h` (`wine_server_call`; see "Tests").
  The layer finds the same exports by ordinal (`core/dispatch/internal.h`, `wine_ordinal::`): the unix call dispatcher and
  unixlib handle in `process.cpp`, the four `__wine_dbg_*` overrides in `rtl_forward.inc`.
* **(b) No debug machinery.** `build.sh` builds with `-O2 -DWINE_NO_TRACE_MSGS -DWINE_NO_DEBUG_MSGS` (and without `-g`,
  with `-ffile-prefix-map` for the source and build trees). `patches/0005` makes `WINE_NO_DEBUG_MSGS` silence `ERR`
  too (Wine's header keeps it "regardless of what is configured"), so no message text and no `__wine_dbch_*` channel name
  remains. Our layer's tracing (`WIN10XBOX_DEBUG`, `WIN10XBOX_WINEDEBUG` is now a no-op for the builtins because they
  print nothing) is separate. No gate depended on a Wine `FIXME`/`ERR` string: the gates assert on our own trace
  (`modules`, `RtlAddFunctionTable failed`, `shot:` lines) or on guest output.
* **(c) Version resources.** `patches/0007`: FileVersion/ProductVersion `10.0.19045.3803`, ProductName
  `Microsoft® Windows® Operating System`, CompanyName `Microsoft Corporation`, LegalCopyright
  `© Microsoft Corporation. All rights reserved.`, FileDescription per module from `wine-pe/version_strings.txt`. Every
  module in `dlls.txt` now has a version resource (kernelbase, win32u, ... had none). **The FileDescription strings were
  written from memory, no Windows file was at hand to compare**: each line of `version_strings.txt` says `recalled` or
  `module` (Windows string unknown, the file name is used: coml2, wbemprox and the console programs except reg, services,
  explorer, conhost). Unverified; a one-off comparison against `C:\Windows\System32` on a Windows runner would settle it.
* **(d) `tests/guest/nowine.c`, `integration.guest_nowine`** (builtin-only machine folder, all three ci.yml jobs):
  walks the modules of its own process (`K32EnumProcessModules` and the PEB loader list; they must agree), checks the
  export names (no "wine", case-insensitive; the genuine names `WinExec`, `LsaNtStatusToWinError`, `*WinEvent*` are not
  counted), the version resource (no "Wine"), every read-only data section (no ASCII or UTF-16 `Wine `, `wine_`, `WINE`;
  `WINEVENT` not counted), and that `GetProcAddress(ntdll, "wine_get_version")` is NULL; prints one line per module,
  exits 42. It runs on ntdll, kernel32, kernelbase and ucrtbase (what a console program loads). `nowine.exe all` loads the
  rest of the set first and lists what they still say (not gated, see below). Under Wine the guest's module list holds only
  our builtins: the host's ntdll does not leak into it.
* `patches/0008`: names that only Wine's plumbing used and a program can see: `wine_threadpool_*` thread names,
  `\\.\pipe\wine_pty_signal_pipe%x`, the `WINE*` environment variable names of the unix side (renamed `NTSYS_*`; the
  layer never set them and drops `WINE*` from guest environments), the `WINE_REGISTRY` resource type (now `REGISTRY`, in
  every .rc, widl, setupapi, winecrt0's registrar), the `Wine builtin DLL` signature in the DOS header (winebuild writes
  it, ntdll's loader reads it; now `System builtin DLL`), `__wine_vxd_*` lookups, and the CRT abort dialog.

## Tests

The Wine conformance suites ask ntdll whether it is Wine's (`running_under_wine()`: `GetProcAddress(ntdll,
"wine_server_call")`) to decide whether `todo_wine` applies; without the name they believed they ran on Windows and
the baselines (recorded with `todo_wine` on) regressed (ntdll rtlstr, kernel32 path, msvcrt). `include/wine/test.h` (the
test framework, not a shipped module) now asks by ordinal. `WINETEST_PLATFORM=wine` would be the framework's own switch
but the layer does not hand `WINE*` host variables to the guest.

setupapi are not built).
Other traces: the file name `wineboot.exe` (its version resource says `wineboot.exe`); the `.buildid` section; section
and import tables are Wine's.
